# 08 战斗质量收口方案（用户反馈六问题）

- 来源：用户 2026-11-09 试玩反馈
- 执行原则：状态机是地基 → 技能组件化在其上 → 手感调校与美术清补收尾；每项有可测验收条件，逐卡执行逐卡验收
- 关联卡：M8-031（状态机+组件化）、M8-032（手感）、M8-033（美术审计清补）

---

## 问题一：没有战斗状态机

### 表现形式
- 角色动作之间没有明确的阶段边界：攻击可以被打断进任意状态、收招期与下一招之间无规则衔接，连招/受击/浮空/倒地的转换看起来"乱"
- 同一技能在不同时机触发表现不一致（有时播动作有时不播）
- 哥布林等敌人的行为与玩家共用零散判断，无统一状态语义

### 现状根因
- `UCombatComponent` 已有 `ECombatActionState`（Free/HitStun/Knockdown/Recovering/Dead）但只覆盖**受击侧**状态；**攻击侧**（待机/前摇/active/后摇/取消窗）由 combat-attacks.json 的帧表数值驱动（active_start_frame 等），没有显式状态机对象，状态转换规则散落在 Tick 与输入缓冲判断里
- 攻击实例（AttackInstance）存在但没有把 [前摇→active→后摇] 作为一等状态暴露；显示层（DNFMCombatVisualPresenter）靠帧段表反推当前阶段

### 解决方案
1. 新建 `UCombatStateMachine`（ActorComponent）：
   - 显式状态集：`Idle / Windup / Active / Recovery / CancelWindow / HitStun / LaunchAir / Knockdown / GetUp / Dead`
   - 合法转换表（数据驱动，Data/CombatSystem/scene 状态表），非法转换拒绝并记日志
   - 每帧 tick 推进：帧表数值（active_start_frame 等）仍为唯一事实来源，状态机是它们的显式封装
2. `UCombatComponent` 改为向状态机查询当前阶段（对外只读），输入缓冲的取消/衔接判断改为"当前状态+转换表"判定
3. 显示层（DNFMCombatVisualPresenter / 敌人显示状态机）改为订阅状态机的状态变更事件，不再各自反推
4. 敌人（MeleeEnemy/Goblin）复用同一状态机类（敌我同构，参数不同）

### 验收条件
- [ ] 自动化：给定输入序列，状态机输出与转换表逐条一致（合法转换通过、非法转换拒绝并记录）
- [ ] 自动化：active 窗口内命中判定开启、窗外关闭，与帧表数值逐帧一致
- [ ] 自动化：HitStun 期间任何攻击意图被拒绝（不播动作不产生判定）
- [ ] 手动：连招 light_01→light_02 在取消窗内衔接、窗外不衔接，观感有明确阶段边界

## 问题二：技能没有做成组件加载的形式

### 表现形式
- 六个技能的行为/弹道/表现散落在combat组件、武器系统、显示层三处，加一个新技能要改多处
- 旧的发射器弹道（M3/M4 武器系统 bullet_linear 等）仍在为技能服务，与 DNF 技能形态不符
- 技能之间没有统一的资源结构（每个技能的特效/声音/弹体/段表各自为政）

### 现状根因
- 技能定义在 combat-attacks.json（帧表+命中盒+衔接链），但**表现资源**（特效/弹体/声音）不在同一结构里：弹体走 M5 武器管线（projectiles.json 的 bullet_* 行+ProjectileWorldService），近战判定走命中盒查询，音效走表现组件——三种装载方式并存
- 无"技能组件"抽象：一个技能=数据行+散落逻辑

### 解决方案
1. 定义 `USkillAbilityComponent`（每技能一个实例，挂角色上）：
   - 自包含：施放条件（状态机状态+冷却+MP）、前摇/active/后摇帧段、命中盒参数、弹体/特效/声音引用、衔接链（next_attack_ids）
   - 数据源：combat-attacks.json 扩展每行 `ability_components` 段（引用特效/声音/弹体资产路径）
2. 输入层只做一件事：把按键意图路由到对应技能组件的 `TryCast()`；组件内部走状态机申请 Windup
3. 旧弹道迁移：launcher 的箭矢从 M5 武器管线改为 launcher 技能组件的弹体参数（直线飞行/命中盒/伤害走统一 Health 链）；bullet_linear 等 M5 行保留给未来武器系统，不再为技能服务
4. 首批组件化六技能：light_01、light_02、launcher、aerial_01 + 两个待定技能（与用户确认技能表）

### 验收条件
- [ ] 自动化：每个技能组件独立施放——TryCast 后状态机进入 Windup、帧表窗口内命中、弹体/特效/声音资源全部从组件数据解析
- [ ] 自动化：移除任一技能组件，其余五个不受影响（组件隔离）
- [ ] 代码：输入层无技能特判（全部经组件路由）；M5 武器管线不再被技能调用
- [ ] 手动：六技能逐一施放，形态/弹道/命中与 DNF 对应技能一致（用户确认）

## 问题三：人物攻击没有战斗手感和节奏感

### 表现形式
- 攻击命中无停顿/无反馈冲击，连打像"打空气"
- 攻击间隔与动作节奏不匹配（前摇后摇比例失调）
- 命中时无镜头/音效/受击反馈的叠加冲击

### 现状根因
- combat-attacks.json **已有** hit_stop_seconds（0.04s）、hit_stun_seconds（0.22）数据，但 hit stop 只作用于受击者冻结，**攻击者侧无停顿/无镜头微动**，且 M8-019B 石头伤害路径绕过了统一命中管线（无任何反馈）
- 命中音效已接（M8-021 ft_dmg_01）但攻击挥击音、命中打击音未接（P13 遗留）
- 攻击节奏：帧表数值沿用 M1 设计值，未经手感调校

### 解决方案
1. 命中反馈栈（命中瞬间同时触发）：攻击者侧 hit stop（时间膨胀 0.03-0.06s）+ 受击者 HitStun（已有）+ 命中音（打击音效组件化后接入）+ 受击闪白（敌人已有，玩家命中时对敌人触发）+ 镜头微震（APrototypeCameraShake 基础版）
2. 节奏调校：以 DNF 原作为参照逐技能调 active 帧窗与 hit_stop（light 连打手感：命中即停 0.04-0.05s、第三 hit 加大）；数值改动落在 combat-attacks.json（数据驱动）
3. 石头/投射物命中走统一反馈栈（M8-019B 的直连 ApplyDamage 路径升级为带反馈的统一入口，伤害仍走 Health 链）

### 验收条件
- [ ] 自动化：命中帧 hit stop 时间膨胀生效（世界时钟冻结实测）且受击者 HitStun 进入
- [ ] 自动化：投射物命中触发同一反馈栈（闪白+音效调用）
- [ ] 手动：light 连打三连击，每击有停顿/打击音/受击闪白，节奏与 DNF 原作手感对齐（用户确认）
- [ ] 数据：全部调校数值落在 combat-attacks.json（无代码硬编码）

## 问题四：大部分美术资源缺损

### 表现形式
- 场景中大量对象为占位色块/无贴图（工会图部分区域、火山未导入）
- 技能无特效（命中/施放无视觉表现）、无打击感视觉
- HUD 为调试文本面板，无正式 UI

### 现状根因
- 已知缺损清单（部分已修）：工会图贴图已补（M8-024）、竹林完整；**技能特效零导入**（P13 遗留：18 技能特效/图标）、**打击音/挥击音未接**（M8-021 只接了受击声）、**正式 UI 未做**（P11 遗留）
- 火山图资产已提取（M8-027）未导入（M8-028 挂起）

### 解决方案
1. **美术缺损全量审计**：编辑器逐图扫描（竹林/工会/训练/主菜单），产出缺损清单（对象→材质→贴图状态），登记逐项来源
2. 技能特效最小集：六技能各 1 个命中特效 + 施放特效（源图集或简化粒子），经技能组件数据引用
3. 攻击音补接：挥击音（ft_atk_01..03 已在 M8-009 定位）+ 打击音（1st_strong_lowkick_hit/lowKick_impact 已定位）经技能组件接入
4. 火山图导入完成（M8-028~030 恢复执行）后并入审计
5. 正式 HUD 不在本方案（P11 选角/UI 独立工作包），但调试面板加开关

### 验收条件
- [ ] 审计文档：四张图逐对象缺损清单（对象名/当前状态/来源/处置），零"未知状态"项

- [ ] 手动：六技能施放均有可见特效与声音；四张图无纯色占位块（用户逐图确认）

## 问题五：人物模型技能混乱（显示与技能错位）

### 表现形式
- 技能触发时角色播放的动作与技能不匹配/不播/闪烁
- 格斗家图片只有 12 个动作，技能映射存在空缺与借用

### 现状根因
- M6-023 段表把 6 攻击映射到源剪辑段（起手/命中/收招），但映射表只覆盖部分技能帧窗；未覆盖的技能无显示段→ presenter 回退或静止
- 技能新增/改动时段表需手工同步，无一致性校验

### 解决方案
1. 段表一致性校验入自动化：combat-attacks.json 每个攻击 id 必须有显示映射，段覆盖 [0, DurationFrames) 无空洞（M6-023 已有校验器，扩到全技能）
2. 缺失映射补齐：从火山/格斗家源图集再提取缺失动作帧（M8-010 管线）或明确降级策略（借用最近似动作+标注）
3. 技能组件化后（问题二），显示映射随组件数据走（组件持有自己的段表）

### 验收条件
- [ ] 自动化：全技能段表覆盖校验绿（无空洞、无缺映射）
- [ ] 手动：六技能逐一施放，动作与技能语义一致（用户确认）
- [ ] 数据：每个技能的动作映射来源（源剪辑名）记录在组件数据中
