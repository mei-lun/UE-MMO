# 任务执行与交接规则

这份规则适用于 ZCode、CodeBuddy、Codex 或其他接手本仓库的编程 Agent。每个任务卡的目标是一个可独立验收的结果；任务不是按文件数量或代码行数计算。

## 1. 四个文件各管一件事

| 文件 | 用途 | 是否保存任务状态 |
|---|---|---|
| 根目录 TASKS.md | 全部任务、依赖、负责人、更新时间、证据入口 | **唯一状态来源** |
| Docs/Tasks/M1-xxx.md 等任务卡 | 边界、接口、实现步骤、验收条件 | 不保存进行中/完成状态 |
| Docs/Tasks/Reports/任务ID.md | 实际改动、命令、结果、提交与限制 | 记录证据，不建第二张进度表 |
| 根目录 HANDOFF.md | 最近批次总结、正在做什么、如何接续 | 只引用总表，不覆盖其状态 |

Docs/05-验证记录.md 是里程碑级实际验证摘要。每项的小测试写任务报告，每个阶段或测试方式变化时再更新它。旧 Docs/06 的大任务仅作设计背景，不再勾选其复选框。

## 2. 一次做几项、什么时候更新

**一次只领取 1 项。每完成 1 项立即更新总表和报告；连续完成 3 项之后写一次批次交接；不足 3 项退出也必须写。**

默认一轮 AI 会话最多完成 3 项后返回用户。用户明确要求连续执行更多时，每 3 项保存一次交接检查点后可继续，但任何一项的总表更新都不能延迟。前置未完成的任务不要为了凑够 3 项硬做。

完成计数只统计本轮新增 `DONE` 的任务 ID。既有 M0、仅改文档的状态整理、被拆分为 `SUPERSEDED` 的父任务、不通过的验收均不算新完成。可部分实现，但不记录“70% DONE”。

任务预估实现超过 90 分钟或同时涉及两个可单独拒绝的行为时，在继续实现前拆成更小任务。新子任务 ID 用 `M1-031A` / `M1-031B` 等后缀，原任务状态设 `SUPERSEDED`，报告列替代项；更新所有下游依赖到实际子任务。一个正常验收任务不为追求数量拆成“改一个字段”而失去独立意义。

## 3. 状态的精确定义

| 状态 | 使用条件 | 后续动作 |
|---|---|---|
| TODO | 未开始；依赖未满足也维持此状态 | 依赖全 DONE 后可领取 |
| IN_PROGRESS | 已领取，正在有实际进展 | 填 Owner、更新时间与报告入口 |
| PAUSED | 已停止工作、部分完成，下一 Agent 可续做 | 留文件/步骤/验证缺口，不能假定已完成 |
| BLOCKED | 需要外部条件，如缺资源、基线失败或必须的决定 | 报告具体障碍与解除条件；能做的独立任务可继续 |
| REVIEW | 人工验收已准备好，等待用户实际反馈 | 不能由 AI 编造认可 |
| DONE | 本卡全部验收满足、证据已记录、代码已进入当前工作分支 | 允许其依赖继续 |
| DEFERRED | 当前范围外，不自动领取 | 用户扩大范围并补充设计后转换 |
| SUPERSEDED | 已被更细子任务替代，旧 ID 保留追溯 | 不算完成；下游不得继续依赖父 ID |

推荐流转：`TODO→IN_PROGRESS→DONE`；中断时 `IN_PROGRESS→PAUSED/BLOCKED`；人工项 `TODO→REVIEW→DONE`。失败人工验收回 `BLOCKED` 并记录问题，不取消已经真实通过的技术任务，新增针对性的修复任务。

## 4. 开始前

1. 读取 AGENTS.md、TASKS.md、HANDOFF.md、接口约定与所选任务卡。
2. 执行 `git status --short`、`git log -3 --oneline` 和 CheckTaskBoard。
3. 如果存在他人未提交修改，记录其范围；不能 reset/clean 或覆盖以制造干净状态。
4. 同一目录有 `IN_PROGRESS` 时，先读取其报告；确认是自己续作，或先记录接管原因再转移 Owner。时间过久不等于允许覆盖他人工作。
5. 选依赖全 DONE 的最小 ID；特殊情况下可选独立任务，必须在报告中解释。
6. 将总表改 `IN_PROGRESS`，写唯一 Owner（如 ZCode-20260925-A）、当前 ISO 时间、报告链接；从模板创建任务报告，记录当前 HEAD 作为 Baseline-Revision。

## 5. 每项完成定义

以下全部满足才能 DONE：

- 本卡范围内的正例、负例与边界验收已执行。
- 所有必要构建/资产重载/运行/画面检查有本次证据；0 个测试、旧截图、只有编译成功都不能代替实际验收。
- 任务报告解释每项断言结果和已知限制；相关文件清单明确。
- 实现已保存到当前工作分支，并有可解析 Git 提交；外部分支只完成而未集成时，不能解除当前分支的依赖。
- 更新 TASKS 对应行，引用报告；运行 CheckTaskBoard 通过。

建议提交顺序，避免报告引用“自己这次提交”的循环：

1. 完成代码/测试，保留总表 IN_PROGRESS，提交实现：`feat(M1-003): add bounded input buffer`。
2. 用实际 `git rev-parse HEAD` 写报告 `Implementation-Revision`，保存证据/结果；把任务设 DONE，提交状态：`docs(M1-003): record verified completion`。
3. 无代码的检查/素材审查项可以引用被验证的当前代码提交，不伪造新功能提交。只有当前任务自己的改动才能提交，不能捎带别人工作。

原始大日志/视频放 `Artifacts/Tasks/<ID>/<timestamp>`，仓库里长期保留精简文字摘要和可重跑命令。Artifacts 默认不随 Git 迁移，所以报告不能只写“看本机某日志”；必须记录用例名、断言、数值/结果与代码提交。后续机器没有原始文件时可重跑，不默认一切已经通过。

## 6. 人工验收

`M0-H01` 真实键盘和镜头、`M1-H01` 连招手感、`M2-H01` 刷怪、`M3-H01` 成长循环，均由用户本人验收。

AI 可以准备操作步骤、演示与包，并填 REVIEW。只有用户明确表示通过后，才能填报告字段 `Human-Approved: yes`、反馈时间与原话摘要，并改 DONE。没有回复、超时、测试通过均不是用户认可。

M0-H01 暂时不阻止技术性的M1前期工作，但M1阶段最终验收依赖它。M2必须等M1-H01通过，M3必须等M2-H01通过。遇到人工关卡时写交接返回用户，不连续询问同一个问题。

## 7. 会话交接

HANDOFF 每批覆盖为最新摘要，历史批次另保存 `Docs/Tasks/Handoffs/<date>-<owner>.md`。内容至少包括：

- 本轮 Owner、开始/结束时间、起止提交。
- 本轮完成数量和 ID，未完成/暂停/阻塞 ID。
- 当前分支、工作区是否有未提交改动及其所有者。
- 本次验证命令与证据入口，已知限制。
- 接下来应领取的 1–3 个任务及推荐顺序。
- 需要用户决定或试玩的事项；没有则明确“无”。

退出前不要留下“正在进行但没有说明”的状态。做了一半就 PAUSED，并把剩余步骤写到足够别人接续；不能为交接好看标 DONE。

## 8. 顺序接力与同时开发

默认是**多个 AI 顺序接力**。本机同一UE工作目录、二进制资产和总表同时只允许一个写入者。本次没有实现跨进程锁或跨工作树任务调度。

如果用户以后要求同时开发：先由用户指定一个协调者，集中领取/更新根总表；实现者使用独立 Git worktree，任务之间不能改同一组资产或接口。协调者合并、验证后才标 DONE；依赖方不能只因另一个 worktree 声称通过而开始。不要自行同时启动多个写同一地图的 UE。

## 9. 检查脚本能做什么

`Scripts/CheckTaskBoard.ps1` 是只读检查器：核对ID、状态、依赖存在、环、报告存在、当前进行中数量、DONE依赖、统计与可领取任务。可运行 `-Json` 供Agent读取。`Scripts/UpdateTaskStatus.ps1` 按ID更新一行并立即调用检查器；如果报告/依赖不满足，它会失败并要求修复。

它不能判断代码是否正确、截图是否好看、人的反馈是否真实；格式检查通过不自动把任务变成DONE。执行者仍承担验证和如实记录责任。

## 10. 给任何新 Agent 的统一提示

```text
打开 D:\Github-Poj\UE-MMO，先读 AGENTS.md、TASKS.md、HANDOFF.md、
Docs/Tasks/执行与交接规则.md 和 Docs/Tasks/接口约定.md。
检查 git status 和 Scripts/CheckTaskBoard.ps1。
从依赖全部 DONE 的最小 TODO ID 开始，一次只领取一项。
本轮最多完成3项，每完成1项立即填写对应报告并更新TASKS.md，
完成3项或提前停止都写HANDOFF和历史交接记录。
严格按任务卡独立验收，未通过或未验证不能标DONE。
不开始联网、不重建工程、不生成角色美术、不覆盖其他AI的改动。
人工验收任务只能等待用户真实反馈，不能自行代签通过。
本轮结束报告：完成多少项、具体ID、验证证据、未完成项和下一任务。
```
