## 目的

实现 M3-009：满包时保留待领取奖励。为 `URewardService` 增加 `TryClaimPending` 领取入口：

- 背包装得下的待领物品按预生成 InstanceId 逐件入包；装不下的保留在 `PendingRewards` 草稿中（原 ID/词条不变，不随机刷新）。
- XP 每 Settlement 只授予一次（首次领取即授予并记录到 `AppliedSettlementIds`，满包也不扣住 XP——XP 是结算进度，不是背包载荷）；重复领取经验总增加 50 而非 100。
- 全部领完后草稿从 pending 移除，但已结算 ID 记录保留（`IsSettlementApplied` 语义，M3-008 BeginReward 重放路径据此返回 AlreadyApplied + 空草稿）。
- 未知 SettlementId 明确失败；重复调用安全。磁盘原子性归 M3-016，本卡不涉及。

## XP 幂等实现说明

XP 授予以 `AppliedSettlementIds` 为唯一机制：首次领奖尝试（找到草稿）时 `AddXP(Draft.XP)` 并 `MarkSettlementApplied`；此后同 SettlementId 的任何领取（重复点击、腾格重试）经 `IsSettlementApplied` 短路跳过 XP。满包首领也授予 XP（XP 不占背包格），腾格重试只补物品——两种时序下经验总增量均为 50。设计取舍已在 RewardService.h 的 TryClaimPending 注释中写明。

## 已知限制

- `TryClaimPending` 拒绝路径含 Duplicate/InvalidInstance 时同样保留物品并返回 InventoryFull（Error 注明非满包拒绝）；正常数据流不会触发（草稿实例均为合法唯一 FGuid），未单独立枚举值。
- 满包首领会先授予 XP 再报告 InventoryFull；调用方需按 Result 显示 InventoryFull、按 bGrantedXP/XP 显示经验（报告为设计取舍，验收未覆盖此细节的 UI 呈现）。
- 内存语义：本卡不做磁盘持久化与原子提交（M3-013 存档层、M3-016 原子提交负责）；进程退出即失，符合当前阶段设计。
- 自动化测试不覆盖真实 UI 点击；"显示 InventoryFull" 以返回枚举与 Error 文本为验收面。
- 测试 6（多件草稿）通过 `GetPendingRewards()` 直接注入 2 件草稿（BeginReward 每结算固定 1 件），用于锁定接口的多件部分成功语义，已在测试注释中说明。
