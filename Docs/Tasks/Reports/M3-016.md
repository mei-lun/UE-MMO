## 目的

奖励领取必须与 AppliedSettlementIds、背包、XP 作为同一个 Profile 快照持久化（接口约定第 8 节）：保存成功才允许向 UI 确认领取成功；保存失败不得半领、重复领、不得重掷原结果。本卡交付 `URewardService::ClaimPendingAtomic`，把 M3-009 的内存领取升级为"先持久化奖励草稿 → 内存领取 → 持久化领取快照"的原子提交，并用三个中断注入点 + 重启验证持久化幂等。

  - `TryClaimPending` 的内存语义（步骤原样、错误文案不变，M3-009 测试锁定）提取为 `M3_016_ApplyClaimInMemory`；`TryClaimPending` 仅保留绑定守卫后委托。
  - `ClaimPendingAtomic` 有序流程：
    1. 显式参数守卫（无 Profile/无已建档 → RejectedNoProfile；无 SaveService/未初始化前缀 → RejectedNoSaveService）；
    2. 持久化状态幂等门：无草稿且有 applied 记录 → AlreadyClaimed（不存盘、不变更）；无草稿且无记录 → UnknownSettlement——判断只来自 Profile 当前状态（重启后即恢复自存档的状态），不依赖调用历史；
    3. `LoadActiveProfile` 读取最后已提交存档（携带 applied 集合与装备绑定）；全部损坏（FailedCorrupt）→ RejectedUnreadableSave，拒绝在损坏证据上保存；
    4. SAVE A（草稿先持久化，"StartRoom 语义"的存档含 PendingRewards）：失败 → SaveFailed，此时未做任何内存变更；
    5. 从草稿内存领取（共享体：XP 恰一次 + MarkSettlementApplied、物品按原 InstanceId 入包、拒绝项保留）；
    6. SAVE C（领取后快照一次性保存：XP/背包/剩余草稿/applied 集合）：失败 → `RestoreFromSave` 回滚内存到 SAVE A 提交的确切状态（并回推装备加成行），计数器按"净效果"归零（ClaimedItemCount=0、bGrantedXP=false、草稿保留原物品），返回 SaveFailed——UI 永远不会看到领取成功；不重掷原结果；
    7. 保存成功才返回 Claimed/PartiallyClaimed/InventoryFull 且 bSaveCommitted=true（满包保留属于"已持久化、未领成"状态，UI 显示保留而非领取成功）。

## 已知限制

- `M3_016_MakeRequestFromProfile` 的 AppliedSettlementIds/EquippedMap 取自"最后一次已提交存档"（LoadActiveProfile），再合并本次领取的 SettlementId——因为 `UProfileSubsystem` 只暴露 `IsSettlementApplied/MarkSettlementApplied`，无法枚举全集。若未来的接线任务在领取流程之外 MarkSettlementApplied 且不落盘，该标记不会被原子领取的快照携带；建议后续给 ProfileSubsystem 增加只读枚举接口（属于其他任务卡，未改）。
- 领取快照保存失败后的内存回滚复用 `RestoreFromSave`：装备加成行会被重置，已捕获并在回滚后原样回推（`SetEquippedStatBonus`）；与 M3-015 恢复语义一致。
- "索引前"中断点建模为"索引提交撕裂"（存储接受了写坏内容的索引文件）：与"写槽后"（索引未写）的磁盘提交态相同，但覆盖了重启世代扫描回退的独立恢复路径；三种注入点合起来覆盖领取快照保存可能留下的全部磁盘状态。
- 撕裂索引用例中，服务在调用时点看到的是装饰器返回的"写入成功"，故首次调用返回 Claimed（真实磁盘撕裂写同样可能如此）；正确性由重启后的世代扫描保证——测试已按此断言并在用例注释说明。
- 测试为自动化断言，不覆盖真实键鼠输入与真实试玩；无画面变更，未跑 Render。
