## 目的

修复协调者审计发现的两个 P0 缺口：

1. **新玩家首次启动没有 Profile**。GameFlow 的 NoSaveFound 分支从不建档（M3-017 注释"never automatic"），生产代码唯一 NewProfile 调用在 HUD 调试路径——首启玩家领奖 ClaimPendingAtomic 被 RejectedNoProfile 拒绝、成长链断裂。本卡确立语义：**NoSaveFound 不是失败，是首次启动的合法状态，此时 NewProfile 是正确动作**；RecoveryError（损坏数据）保持不建档，M3-015/M3-003 语义不变。
2. **敌人攻击玩家的完整链路（Telegraph→Attack→玩家受伤→死亡→Failed→Retry）从未在真实循环中验证**。本卡以生产 WaveSpawner 接线（M3-025）+ 真实 Tick 在环驱动全链。

与 M3-003 规则的边界（报告存档）：M3-003 要求"载入失败不得自动 ResetNewGame/NewProfile"。本卡不违反它——`EStartupLoadResult::NoSaveFound` 的语义是"什么都没存过"（接口约定第 8 节：由调用方决定），不是失败；`GameFlowSubsystem::Initialize` 就是那个"调用方"，在真实 StartupLoad 返回 NoSaveFound 时显式建档。`RecoveryError`（数据存在但不可用）与 M3-015 一致：保证据、不建档、绝不静默重开。自动化未注入存储服务时综合出的 NoSaveFound 是测试隔离标记，**不建档**（M3-003"干净 GameInstance 无档"保证保持，ProfileTests 等既有断言不受影响）。

## 已知限制

- 自动化中 NoSaveFound→NewProfile 仅在**真实 StartupLoad 运行**时发生（注入隔离存储或生产 Profile_ 前缀）；未注入服务的自动化综合结果不建档（M3-003 保证）。真实磁盘路径（Profile_ 前缀）的建档代码与测试同分支，但真实读写只在用户试玩/生产启动时发生，自动化未触碰用户存档。
- 死亡/重试场景使用单敌房间：多敌人会在首个攻击者周围产生分离驻留振荡，使"敌人打死玩家"的时序不确定（红灯轮实测）。完整循环场景仍用生产 2+3 波形——首个到达者攻击周期确定，其余敌人滞留不影响断言。
- 敌人攻击链在"真实 Tick + 生产 WaveSpawner 接线"下验证；自动化无键盘输入，玩家操控下的受击体验仍属 H01 用户试玩边界。
- 本卡未覆盖玩家真实连招输入击杀（击杀走合法致命 ApplyDamage，与 M2-014/M3-020 先例一致；玩家侧真实攻击伤害测量已由 M3-020 锁定）。
- `EStartupLoadResult::NoSaveFound` 语义变化只动 GameFlow 一处；若未来出现"菜单内显式开新档"需求，应走显式 NewProfile/ResetNewGame 入口（M3-003 API 不变）。
