## 2. ID 与事件

```cpp
struct FCombatEventKey {
    FGuid WorldEpoch;
    FGuid SourceEntityId;
    uint64 ActionSequence = 0;
    int32 PelletOrHitGroup = 0;
    FGuid TargetEntityId;
};
struct FHitRequest {
    FCombatEventKey Key;
    FName WeaponDefinitionId;
    FName DamageProfileId;
    FName AttackReactionId;
    FGuid WeaponItemInstanceId;
    FGuid ProjectileInstanceId;
    FVector HitLocation;
    FVector Direction;
    int64 SimulationTick = 0;
    FString ConfigRevision;
};
struct FHitOutcome {
    EHitDecision Decision;
    float AppliedDamage = 0;
    bool bControlAccepted = false;
    bool bKilled = false;
    FName RejectReason;
};
```

实际UE反射/委托由002按本机编译确认，字段语义不可随意改。伤害倍率/装备属性由服务解析合法上下文，不让外部请求指定最终扣血。ActionSequence由010注册表按(Epoch,SourceEntity)统一分配，近战/远程/载具动作共用单调序列。旧AttackInstanceId和局部ShotSequence仅作关联字段，不能直接用作公共序列；不同能力局部序列都为1时仍须产生不同公共Key。EventId由完整Key稳定派生，不用指针值。

运行时接收旧Epoch、未知实体、注销后目标、同Key重复请求返回拒绝，无伤害/冲量/表现。一个Shot多个Pellet可分别伤害，控制去重另用 `(Epoch,Source,ActionSequence,Target)`，不能让霰弹绕过浮空限制。Ledger会话结束清理，不能淘汰尚活跃Shot/Attack的Key以允许重复命中；硬容量达到后拒绝新的攻击，不能静默破坏幂等。


签名中值类型由标注所有者补齐并冻结。公共Outcome用明确枚举，禁止只有bool而丢失原因。WeaponComponent在022定义调度接口，023/024/025扩展策略并通过接口注册；ProjectileActor在027/028定义唯一推进和命中策略接口，029..032仅提供策略。

## 4. 时间与空间

攻击帧/输入沿用现有60Hz逻辑和150ms缓存语义；HitStop补偿按当前M3实现。反应截止读其现有输入时钟；弹道与火器冷却用Pause冻结的World时间。SimulationTick只作本机单调事件标签，由002规定采样，不替代任何截止时间或服务器时钟。

X横向、Y纵深、Z高度，Facing±1只镜像X。发射偏移从脚底；Hit/Knockback/Launch方向是世界向量，不从Yaw猜纵深。所有角度/速度/尺寸附单位。

## 5. 状态唯一来源

保留 CombatComponent 为状态/计时所有者，HealthComponent为生命所有者。ReactionResolver返回是否接受、冲量、硬直/倒地/恢复参数，不直接改另一套State。生命/动作/运动三个维度保持原接口。免疫和霸体不是新动作枚举；CanMove/CanTurn/CanAttack由CombatComponent统一查询。

默认硬直覆盖max；死亡最高优先；旧实例中断立即失效；起身默认拒绝整次命中。普通跳跃不倒地。Damage与Control分别接受；控制免疫仍可伤害，纯控制不制造虚假伤害事件。默认浮空两次1.0/0.7与0.45/0.25秒恢复不变。

## 6. 表、资产和版本

源表只有JSON一种，顶层schema_version/table/rows。required_tables与支持能力在manifest明确列出。源路径 `Data/CombatSystem`；输出 `Content/UEMMO/CombatSystem`，资源相对引用第三方仍保留原路径。Python只在UE编辑器执行，资产必须保存后新进程重载。

既有Data/items.json/drops.json沿其Schema规范化导入，只有一份权威源。Catalog还提供FItemDefinitionCatalog/FDropTable适配与TestRoom reward/spawn定义；生成资产覆盖这些内容。生产HUD/RewardService在020A接入，缺ID拒绝。测试fixture的固定替身不能继续成为新内容的唯一生产获取途径。

Catalog软引用纳入明确Cook列表和配置引用；缺任一required资源拒绝目录启动。展示可选资源缺失可以文字回退，但日志明确且不算素材已完成。ConfigRevision对规范化合法源表SHA256，保存/事件/包manifest使用同一revision。

## 7. 存档与实例

WeaponDefinition通过item_definition_id绑定FItemDefinition；FItemInstance仍是唯一物品身份，不复制一个武器Item。`WeaponStateByItemId`仅记录该实例弹匣，`ReserveAmmoByType`记录共享备弹；切装备不初始化新弹药。

v2新增这些值类型和revision，A/B完整性计算覆盖新字段。v1读取可用、v2迁移写新槽并读回后改索引；已应用领奖ID和实例ID不变。未来版本/未知业务引用拒绝并保留文件。完整派生属性和WeaponComponent在角色BeginPlay/换地图重绑，不存瞬态Actor。

历史accessory_training->charm_training由manifest显式别名承载，046保持原InstanceId/RolledStats/装备引用；别名校验无环、目标存在、revision覆盖。别名不是允许任意未知定义回退。

ConfigRevision是溯源值，不自动拒绝所有旧档。新目录只增行且旧ID/状态约束仍兼容时加载旧v2档，按当前目录重绑，不重新发初始弹。Ammo类型变化、容量小于已装弹等不兼容变更拒绝并保留槽，除非另有显式迁移卡。048必须用新增配置前的已保存v2档验证，不只在新revision创建档再重启。

首版近战武器attack_ids只能引用现有light_01/light_02/launcher/aerial_01完整集合，X/Z取消链不因换装备更换招式；武器属性/外观及配置反应可变化。未知/不完整AttackSet在校验阶段拒绝，不能读取后静默忽略。任意近战招式集切换以后单独拆卡，不新增一套计时器。

## 8. 载具权限

VehicleActor复用HealthComponent与TryApplyHit，有自己的EntityId。SeatModel原子占用，World只能一实体占一个座；输入在041交接，Movement在042持有，Mount在043使用WeaponComponent。共享VehicleActor挂点由各任务串行集成。

当前操作者与发射车辆分别在ShotContext记录，友伤过滤用操作者阵营，无操作者用车辆阵营。清理必须覆盖死亡、销毁、LeaveRoom、Retry和World EndPlay。
